# QMemory 使用方评审：把记忆从“必经流程”变成“按需基础设施”

日期：2026-09-10
评审角色：下游项目使用方 / 客观评价方（以 OpenDesign Docs 的真实开发协作为样本）

## 结论

QMemory 对跨会话、跨 Agent、跨设备的长期项目有明确价值，但不应该成为每一次本地开发操作的必经流程。

它最适合保存少量、稳定、可追溯的项目判断：已确认决策、约束、验证过的环境事实、事故原因与修复、阶段状态和交接。它不适合记录每次读文件、改样式、跑测试、查看日志或没有形成新判断的过程。

当前主要问题不是“记忆是否值得做”，而是默认调用链偏重、项目上下文召回过于依赖查询字面匹配。使用方建议将默认流程从“每轮同步、召回、补搜、写入、交接”收敛为“一次条件式启动 + 一次差异式结束”，简单任务零调用，实质开发最多两个 QMemory 往返。

## 使用方证据

### 1. 已验证的价值

- `memory_propose`、`memory_confirm`、`memory_get`、`memory_search` 可以完成判断的提出、确认、查询与追溯。
- 项目隔离、确认状态、替代链和来源引用，是普通文档或聊天搜索无法稳定提供的能力。
- OpenDesign Docs 在跨多轮开发中确实需要恢复产品边界、当前版本、验收口径和未完成事项；这些信息适合进入 QMemory。

### 2. 已复现的缺口

- 一条 OpenDesign Docs 阶段记忆已被明确确认，`memory_get` 和 `memory_search` 均能取回；但带有自然语言任务查询的 `project_context` 返回空列表。
- 当前 `project_context` 直接复用全文搜索；FTS 查询把空格分隔的所有词用 `AND` 连接。只要记忆正文没有同时包含查询中的全部词，就可能漏掉本应在项目启动时出现的已确认状态。
- `agent_conversations_sync` 本次扫描 334 段会话，其中只有 4 段新增，仍复制约 99.6 MB。增量归档是有效的，但把全量扫描固定放在每个实质任务开头，对本地开发过重。
- 使用方近期一组专门讨论 QMemory 的交互中，11 个相关模型/工具往返约占同期有效 token 消耗的 20.5%。其中 QMemory 返回正文估算只有约 7,000–8,000 token，主要成本来自额外往返反复读取长上下文，而不是记忆正文自身。

上述数据来自高负载、长会话且主题正好是 QMemory，不代表日常平均成本；但它清楚说明了应优先减少往返次数，而不是只压缩单次返回文本。

## 本地开发是否需要调用 QMemory

### 应该调用

| 场合 | 调用目的 | 建议动作 |
|---|---|---|
| 隔天、换设备、换 Agent 或压缩上下文后继续项目 | 恢复产品边界、决策、约束、事故与当前交接 | 一次条件式 `project_context`；仅在归档过期时同步 |
| 修改架构、数据模型、部署方式、兼容策略前 | 避免违反既有决定或重复走失败路线 | 按主题召回决策、约束和事故；高风险时再读来源 |
| 用户明确作出或批准长期有效的判断 | 让后续 Agent 能稳定继承 | 搜索去重后 propose / confirm 或 supersede |
| 故障根因和修复经过验证 | 避免重复排障 | 记录一条含证据的 incident |
| 阶段结束且状态发生变化，或仍有明确未完成项 | 给下一位 Agent 可执行的接续点 | 写一条短 handoff，替代旧 handoff |

### 不应该调用

| 场合 | 原因 |
|---|---|
| 简单问答、翻译、格式化、自包含任务 | 不依赖项目历史，调用只增加延迟和 token |
| 每一次读文件、编辑、测试、构建或查看日志 | 这是短暂执行轨迹，不是长期判断 |
| 同一会话中的紧密 edit-test-edit 循环 | 当前上下文已经拥有最新状态 |
| 当前项目没有新决策、事实、事故或交接变化 | 不应制造重复记忆或空 handoff |
| 仓库中已经有完整报告、规范或 changelog | QMemory 只存摘要和文档指针，不复制全文 |
| 密钥、密码、token、个人敏感数据 | 永不进入记忆；脱敏也不能替代最小采集原则 |

## 建议的目标流程

### 当前流程

`同步全部来源 → project_context → 召回为空时 memory_search/get → 执行开发 → propose/confirm → session_handoff`

它的问题是：本地开发的每次启动都承担同步成本；召回失败会触发补搜；结束又容易产生重复状态，最终造成多次模型往返。

### 建议流程

`判断是否需要记忆 → 条件式 bootstrap（内部按新鲜度决定是否同步）→ 返回有上限的项目简报 → 执行开发 → 仅在状态有差异时 commit memory/handoff`

默认预算：

- 简单、自包含任务：0 次 QMemory 调用。
- 同一会话的连续本地开发：通常 0–1 次，只在决策前精确召回。
- 隔日或跨 Agent 的实质开发：最多 2 个工具往返，启动 1 次、结束 1 次。
- 启动返回中位数小于 800 token，P95 小于 1,500 token。
- 在约 200k 长上下文会话中，每个开发回合的 QMemory 有效开销不高于约 40k token-equivalent；在新会话中不高于约 10k。

## 整改优先级

### P0：先修可用性与调用成本

1. 修复 `project_context` 的召回策略。
   - 已确认、当前有效的 `decision`、`constraint`、`incident`、最新 `status` 和最新 `handoff` 应形成项目启动基线，不应因为任务查询缺少完全字面交集而全部消失。
   - 查询相关性用于补充和排序，不应成为唯一入口。
   - 返回 `why_selected`、`status`、`source_ref`、`commit_sha` 和 `stale`，让 Agent 判断是否需要核验。

2. 新增一个条件式启动接口，例如 `project_bootstrap`。
   - 服务端根据 `last_sync_at`、来源变更指纹和可配置 TTL 决定是否同步。
   - 在一次调用内完成必要的增量同步与有界上下文返回，避免 Agent 发起两个模型往返。
   - 返回 `sync_performed`、`sync_age`、新增会话数、上下文 revision 和估算 payload token。

3. 让 `session_handoff` 差异感知和幂等。
   - 与当前 handoff 语义相同或内容相同则返回 no-op，不产生替代事件。
   - 只允许记录“已变化状态 + 未完成项 + 下一步”，避免整份日报进入记忆。

4. 修改 Agent 协议的硬性措辞。
   - 从“实质任务一律先同步再召回”调整为“跨会话或上下文不足时 bootstrap；同会话连续开发且状态新鲜时跳过”。
   - 简单任务明确零调用；记忆故障必须 fail-open，不阻塞开发。

### P1：提升召回质量与可解释性

1. 建立类型化上下文包：稳定约束与决策、近期状态、事故、当前交接分别设上限和时效。
2. 对 `status` 和 `handoff` 增加过期或复核日期；过期内容不得静默进入上下文。
3. 对工作树、分支、符号链接和相同 Git remote 使用稳定项目身份，同时展示本次解析依据。
4. 写入前给出可能重复或冲突的记忆，优先 supersede，不制造平行事实。
5. 文档只存一段摘要、路径、版本/commit 和验收状态；需要细节时再打开仓库文档。

### P2：用数据管理 QMemory 自身成本

1. 增加使用遥测：工具调用次数、空召回率、补搜率、返回 token、同步扫描量、no-op 比例、帮助/忽略/拒绝反馈。
2. 区分 L0 会话归档、L1/L2/L3 提炼和当前 active memory；“已同步”不能被展示成“已形成项目记忆”。
3. 为下游提供策略档位：`off`、`compact`、`full`，默认使用 `compact`。
4. 建立固定下游样本：至少包含 OpenDesign Docs 的跨日续作、故障修复、纯 UI 微调和简单问答。

## 验收标准

### 功能门槛

- 对预置的已确认决策、约束、事故、状态和 handoff，用 20 种同义任务问法测试，`project_context` Top-5 命中率至少 95%。
- 有 active memory 的项目，非刻意无关查询下空召回率低于 5%。
- 相同 handoff 连续提交两次，第二次必须是 no-op，事件数不增加。
- 同一项目的 worktree、子目录和 canonical remote 解析一致；跨项目不得误召回。
- QMemory 服务不可用时，本地开发流程继续，且只给一次可恢复提示。

### 性能与成本门槛

- 简单任务 QMemory 调用数为 0。
- 实质本地开发每轮 QMemory 工具往返不超过 2 次；同一会话连续开发的中位数不超过 1 次。
- `project_bootstrap` 返回内容 P95 不超过 1,500 token，召回 P95 不超过 300 ms（不含确有新增文件时的归档）。
- 无来源变化的 bootstrap 不做全量复制，并明确返回 no-op。
- 发布报告同时展示空召回率、补搜率、重复写入率、no-op 同步率和用户帮助率。

## 对 QMemory 项目 Agent 的任务建议

第一轮只做 P0，并用失败测试驱动：

1. 为“已确认状态能被 memory_search 找到、但 project_context 因多词 AND 查询返回空”补充回归测试。
2. 设计并实现 project baseline + query relevance 的上下文装配策略。
3. 为同步增加 freshness/changed 判断，并提供单次 bootstrap 工具。
4. 为 handoff 增加语义明确的 no-op 结果；至少先支持规范化后完全相同文本的幂等。
5. 更新 Agent 协议和指标；跑现有测试、质量报告及真实 OpenDesign Docs 使用方验收。

本评审不建议立刻扩展更多可视化或高阶记忆层。先让“该出现的项目记忆稳定出现、不该调用时完全不调用”，QMemory 才会从额外流程变成真正节省上下文和协作成本的基础设施。
